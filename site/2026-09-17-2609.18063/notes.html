今天的问题：厨房只放得下当天的食材

想象你开一家餐馆，仓库有二百多套菜谱和食材，灶台旁只能放几套。每道菜只用四套，不代表其他食材从世界上消失了。AI 的混合专家模型也一样：它有很多专长不同的计算模块，每生成一小段文字，只调用其中少量模块。

读完这一篇，你应该能区分“每次计算多少”和“总共存多少”，说明提前备货为什么有用，也能解释为什么这篇方法需要额外训练。这里的厨房只是教学类比；神经网络的专家并不一定对应人能直接命名的职业或知识领域。

第一步：先分清权重、状态与计算

模型的权重是训练完成后保存的大量数值，可以理解为固定的计算规则。生成对话时还会积累临时状态，例如之前文字的注意力缓存。两者都要占空间，但来源不同，不能因为压缩了临时状态，就以为固定权重也变小了。

MoE 是 Mixture of Experts 的缩写。路由器给当前输入挑出若干专家，减少本轮计算；未被调用的专家权重仍须保存在某处。论文把问题对准固定权重的存放位置：把多数专家放在 SSD，也就是固态硬盘，只让当前需要的部分进入快内存。

第二步：为什么临时搬货会卡住

输入是当前文字对应的内部数值状态；输出是下一段文字的概率。中间经过许多层，每层需要先知道选了哪些专家，才能从硬盘搬对应权重。若等上一层算完才选下一层，就形成“等结果、搬数据、再计算”的串行链。

这不是简单增加硬盘容量能解决的。仓库再大，厨师每一步都临时跑去拿食材，灶台仍会空着。论文的重要判断是：真正要改变的是读取与计算的先后依赖，让它们可以重叠，而不只是把文件换一个位置。

第三步：把预测直接作为下一次路由

Edge0 增加小型 prerouter，可以译为“提前路由器”。它在处理当前 token 时，根据可用内部状态预测下一 token 某层要调用哪些专家，于是提前发起硬盘读取。这里 token 是模型处理文字的小单位，不一定是一个完整汉字或单词。

最容易误读的细节是：系统不是预测一份名单、随后又按原路由器重新选一份名单。部署时预测结果本身就是实际路由，所以提前装入的专家和真正使用的专家一致。这样减少临时补货，却改变了模型原来的计算路径；预测错误的代价转移到了模型质量上。

第四步：提前一整步，而不只是提前一层

论文采用跨 token 的提前量，是因为只提前一层时，额外同步和预测计算本身可能把节省的时间吃掉。教学上可把它想成：餐馆根据上一张订单提前备下一道菜，而不是锅已经烧热后才让服务员去问仓库。

缓冲区还需要两份轮换：一份给当前计算用，一份装下一步的数据。于是中间状态包括“正在计算的专家集合”和“正在装入的专家集合”。这种流水线增加少量活动内存，换取等待减少，并不是所有内存口径都会同时下降。

第五步：路径变了，必须补偿质量

论文还把权重压成四位数值，叫 int4 量化。压缩和替换路由都会引入误差。作者冻结压缩后的基础模型，训练一个小的低秩补丁 LoRA，并让补丁在真正部署的学生路径上学习。

可以把 LoRA 想成一道菜最后的调味修正，但这只是类比。原文训练有三阶段：先学路由预测，再在学生路径上做监督微调，最后用学生自己生成的数据进行蒸馏。作者报告，只学预测而不做后续修正，部分运行会出现重复、退化的文字。会预测名单，不等于整个模型已经可用。

为什么修正补丁不能随手合并

假设数值只能存到小数点后一位，基础权重是 1.0，学到的修正是 0.02。先相加再重新取到一位，就又变成 1.0，补丁消失；运行时分开计算 1.0 与 0.02，再相加，则得到 1.02。

论文因此把恢复 LoRA 保留为独立计算分支，不把它合并后再四位量化。这解释了“合并模型文件看起来更简单”为何可能损伤质量。真实网络是大规模矩阵，并不等同于这一个小数；我们的算例只展示小修正会被重新取整吞掉这一机制。

论文真正测到了什么

论文表 1 报告：在 24GB Mac mini M4 Pro 上，35B 的 K=4 配置达到 20.4 token/s，MLX 分配器测得的短上下文峰值活动内存是 2.9 GiB。它不是“整台电脑总共只用 2.9 GiB”：文件映射、系统页缓存和进程驻留内存另有口径。

表 3 在另一台 16GB M2 设备做同会话对照，K=4 时按需加载为 3.5 token/s，提前路由为 6.4 token/s。表 2 的五项基准平均成绩仍低于半精度教师约四个百分点。作者称质量接近，我们更谨慎地理解为：在所测任务和设备上，用可观测的质量差距换取了运行条件改善。

什么时候这个办法不一定划算

若全部权重本来就能轻松放进快内存，磁盘预取的收益会缩小。若硬盘很慢、上下文很长、缓存状态不同，瓶颈也可能转移。论文明确采用同会话轮换对照，是因为单次测速和跨会话结果有明显波动。

我们的推断是，部署决策至少要同时看正确性、质量、吞吐、首轮等待和内存口径，不能只拿一项漂亮数字。这里没有下载或训练 350 亿参数模型，不能用下面的时间算例宣称验证了论文的速度。它只帮助你看懂“重叠哪两件事，代价落在哪”。

沿一份输入走完整条链路

设一次需要四个专家。当前 token 的内部状态进入提前路由器，产生下一步专家编号；读盘线程把相应权重装到备用槽位；下一步开始时交换槽位；基础计算与小补丁相加，得到后续状态。最后模型给出下一个 token 的概率。

这条链最关键的中间状态不是最终一句回答，而是专家编号、缓冲区内容和被替换的路由。排错时可以分别问：装入的专家是否与实际使用一致？等待是否真的与计算重叠？修正补丁是否保留下来？把问题分开，才能理解为什么少占空间并不自动意味着快或准。
